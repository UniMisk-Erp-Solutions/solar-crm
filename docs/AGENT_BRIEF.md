## Architecture in one page
* **Monorepo** (npm workspaces): `packages/shared` (`@solar/shared`: enums, row types, Zod schemas, format/validators, seed), `apps/api` (`@solar/api`: Express 4 + TS, ESM, no `.js` import suffixes), `apps/web` (`@solar/web`: React 18 + Vite).
* **Data access** goes through `ctx.db.table('leads')` → `Repo<Lead>` (`list/all/get/getOrThrow/one/count/insert/insertMany/update/updateWhere/delete`). `ctx.db` is already pinned to the user's organisation (never pass org_id yourself; never use `deps.db`). There is an in-memory implementation (demo mode + all tests) and a Supabase implementation — **write portable code: no raw SQL, no joins**; fetch related rows with extra `ctx.db.table(...).all({ id: [...] })` calls and hydrate in TypeScript. `Where` supports equality, arrays (IN), `null`, and operator objects: `{ due_at: { lte: iso }, status: { nin: [...] }, tags: { contains: ['x'] } }`.
* **No DB transactions.** Order writes so that a failure part-way leaves a recoverable state, and re-check guards in the service layer (the SQL files also contain guard triggers as defence in depth — your service must enforce the same rule and return a friendly error first).
* **Request context**: every route handler receives `ctx: AppContext` via `handle(async (ctx, req, res) => …)` from `http/handler.ts` (returns `{ data }` automatically). `ctx.user` (Profile), `ctx.db`, `ctx.svc` (rules, clocks, notify, consent, messaging, compliance), `ctx.providers`, `ctx.now()` (**always use `ctx.now()`, never `new Date()`** — tests move the clock), `ctx.log`.
* **Services** are plain modules: `export async function doThing(ctx: AppContext, input): Promise<Result>`; routes stay thin (parse → authorise → call service → respond). Services that other modules call through `ctx.svc` (`consent`, `messaging`, `compliance`) are created by `createXService(ctx)` factories.
* **Routes**: each route file `export default`s an `express.Router()` using FULL resource paths (`router.get('/leads/:id', …)`), mounted under `/api/v1`. Name files `<area>.routes.ts`. Public (unauthenticated) routers `export const isPublicRouter = true` besides the default export. **Do not edit `routes/index.ts`** — the integrator registers your routers. In your tests mount them via `createTestEnv({ authed: [router] })` / `{ public: [router] }`.
* **Responses**: success `{ data }`; lists `{ data, total, limit, offset }` (use `runList`/`respondPage`); errors are thrown as `AppError` helpers from `http/errors.ts` and rendered as `{ error: { code, message, details } }`. Validate every body/query with Zod (`body(schema, req)`, `query(schema, req)`); put request schemas that the web app also needs in `packages/shared/src/schemas/<area>.ts` (already exported from the shared index; `export {}` placeholders exist — replace them). Never use `any` in shared code.
* **Authorisation**: `router.get('/x', allow('dsm','sales_manager'), …)` (admin always allowed). Row-level visibility: use `runList` (applies `scopeWhere`) for lists, `assertCanRead(ctx, table, row)` for single rows — external users (`distributor_user`, `dealer_user`) must only ever reach their own party's data. Mask personal data with `maskPii(ctx, row)` in list payloads; revealing a full mobile is a separate audited action.
* **Audit**: every mutation calls `audit(ctx, { action: 'lead.accept', table, record_id, old, new })` from `lib/audit`. (A DB trigger also records raw row changes; your audit rows record business actions.)
* **Rules, never constants**: legal/policy numbers, dates and thresholds come from `ctx.svc.rules` (`rules.path('pmsg.cfa.max_total', refDate)`). Rule path = `<category>.<key>` where category is the first dotted segment. A rule that is `status != verified` or `is_active = false` is **advisory only**: it may produce a warning but must never block or alter a transaction. Use `rules.value()` (null when inactive) for behaviour, `rules.path()` when you need status/confidence/source for display. Turn a violated gate into a severity ONLY through `decideSeverity(rule, baseSeverity)` in `services/severity.ts`. Always provide a sane documented fallback when a rule is absent. Operational defaults your module needs go in your seed fragment (`packages/shared/src/seed/rules.<yours>.ts` as `RuleSeedInput[]`), each with a `source_name` like "Future Solar operating default".
* **Clocks**: `ctx.svc.clocks.start({ entity_type, entity_id, clock_type, due_at, owner_id })`, `.complete(...)`. React to breaches by `registerClockHandlers('lead_acceptance', { onBreach })` from `services/hooks.ts` (call it at module load of your service). All SLA arithmetic respects working hours/holidays via `lib/time.ts` (`addWorkingMinutes`, …) with the `work_calendar.*` rules.
* **Notifications**: `ctx.svc.notify.notify({ roles|user_ids, kind, title, body, severity, entity_type, entity_id })`.
* **Providers** (`ctx.providers`): whatsapp/sms/email/dnd/einvoice/ewayBill/pincode/storage — interfaces in `providers/types.ts`. Application code never calls them directly for customer messages; use `ctx.svc.messaging.send()` (consent-aware).
* **Dates**: store ISO-8601 UTC for timestamps, `YYYY-MM-DD` for dates; IST helpers in `@solar/shared` (`istDateString`, `daysBetween`) and `lib/time.ts`. Money is plain `number` rupees.
* **Privacy**: no Aadhaar numbers/images anywhere (the edge guard blocks JSON bodies; file-name checks via `assertFilenameAllowed`); PII is masked in logs.

## Appendix A — Shared algorithms (SQL, API and web must agree)

**Lead quality score (0–100)** = Σ weightᵢ × factorᵢ (factor ∈ [0,1]). Weights come from rule `scoring.weights` (default, sums to 100):
`requirement_clarity 20, mw_size 15, timeline 25, budget 15, decision_maker 10, consent_present 10, bill_captured 5`.
* requirement_clarity = (requirement_text length ≥ 20 → 0.6, length 1–19 → 0.3, empty → 0) + (segment set → 0.2) + (capacity_kw set → 0.2)
* mw_size by capacity_kw: null → 0; < 3 → 0.3; 3 to < 10 → 0.5; 10 to < 100 → 0.75; ≥ 100 → 1
* timeline by timeline_bucket: immediate 1; within_30_days 0.9; one_to_three_months 0.6; three_to_six_months 0.3; six_months_plus 0.1; unknown/null 0
* budget: budget_inr null → 0; else 1 if capacity_kw is set and budget_inr ≥ 40 000 × capacity_kw, otherwise 0.6
* decision_maker: self 1, family 0.8, committee 0.5, unknown/null 0; if decision_maker_access is false multiply by 0.5
* consent_present: 1 when the lead has at least one consent row with withdrawn_at null, else 0
* bill_captured: 1 when leads.bill_captured is true, else 0
Result = round(Σ). Store the components (`{ key, label, weight, points, note }[]`) in `lead_scores.components` and the total in `leads.quality_score`.

**Lead temperature** from `timeline_bucket`: immediate / within_30_days → hot; one_to_three_months → warm; three_to_six_months / six_months_plus / unknown / null → cold (null timeline defaults to warm until qualified). **Deadline uplift**: raise one level (cold→warm→hot) when a relevant compliance deadline is within `temperature.deadline_uplift_days` (default 60) days — PMSG legacy cohort → `pmsg.claim_deadline.legacy_cohort`; ci_net_metered / open_access → `almm.list2.exemption_net_metering_open_access_until`; set `leads.deadline_uplift = true`.

**Lead acceptance SLA** (clock `lead_acceptance`, owner = assigned distributor user/DSM): hot = `sla.lead_acceptance_minutes.hot` working minutes; warm = `sla.lead_acceptance_minutes.warm`; cold = end of the working day. **Follow-up SLA** (`sla.followup_days.hot|warm|cold` = 1 | 3 | 7 days) sets the default `next_followup_at`.

**Credit exposure / sales-order guard (G11)**: `exposure_after = outstanding(open+overdue dealer_receivables) + max(0, order_total − advance_received)`. Blocked when `exposure_after > dealers.credit_limit` OR the dealer's `portal_status = 'deactivated'` (also `under_sop` → warning at the API, not blocked), unless an approved `credit_overrides` row exists for the dealer (and the PI). Same rule in SQL trigger and in `salesOrderService`.

**Dispatch guard**: a dispatch may not move to `dispatched` while `compliance_status = 'blocked'` unless an approved compliance override exists; and every serial attached to the dispatch must satisfy its segment: `pmsg_residential` / `pm_kusum` need `compliance_snapshot.dcr_verified`; every segment except `ci_captive` needs `almm_list1`; subsidy/government segments (`pmsg_residential`, `rwa_ghs`, `government_bid`) also need `almm_list2` when the expected commissioning date is on/after `almm.list2.effective_date`.

**Opportunity guard**: an opportunity can only be created when `requirement_confirmed AND timeline_confirmed AND commercial_potential_confirmed` are all true (service error `GUARD_BLOCKED` + SQL trigger).

**Consent rules (gate G1)**: promotional message ⇒ needs a non-withdrawn consent covering purpose `promotional` and the channel, `dnd_status = 'clear'` with `dnd_checked_at` newer than `compliance.dnd_scrub_max_age_days` (default 30), and `optout_suppress_until` empty or in the past. Service/transactional messages ⇒ need a consent row covering `service` (or `quotation`) and the channel, OR (WhatsApp) an open 24-hour window (last inbound message < `whatsapp.service_window_hours`). WhatsApp outside the window ⇒ approved template only. Opt-out (`STOP` etc.) ⇒ withdraw all consents, set `optout_suppress_until = now + trai.optout_reconsent_block_days` (90) days, and propagate suppression to every named recipient (distributor/dealer) in a `lead_events` + `audit_log` entry.
